 CHAT / AGENT RUNTIME
=====================================================================
1. Streaming chat (SSE, incremental tokens)
   [YES] backend/app/api/v1/messages.py  (events: start / token /
         done / error); frontend/src/hooks/useNexusChat.ts consumes it.

2. Tool-call events during streaming (AG-UI style)
   [YES] backend/app/api/v1/conversations.py  (emits "tool_call"
         events with tool_call_id; AG-UI-shaped aliases supported).

3. Multi-turn conversation persistence + resume
   [YES] backend/app/domain/conversation/  + /api/v1/conversations.

4. Fork a conversation (continuation of a session)
   [YES] frontend/app/api/conversations/[id]/fork/route.ts
         + backend /api/v1/conversations/{id}/fork.

5. Slash commands + prompt library
   [YES] frontend/src/components/ChatInput.tsx  (slash popover +
         PROMPT_TEMPLATES: code review / research / debugging / arch).

6. Background / long-running tasks
   [YES] Celery worker: backend/app/worker/tasks.py
         (drift scan, webhook redeliver, etc.).

7. Lifecycle hooks (pre/post tool, compact, notification hooks)
   [YES] New hook subsystem: backend/app/domain/hook/ (policy model +
          CRUD repo) + backend/app/services/hook_service.py +
          backend/app/services/tools/hook_registry.py. Hooks run at the
          tool gateway choke point (backend/app/services/tools/
          tool_gateway.py): pre_tool/post_tool policies can block,
          redact, or log tool invocations; tool-name wildcards + org
          scoping (null org = global). Admin CRUD + /admin/hooks/reload
          in backend/app/api/v1/admin.py; registry reloaded on startup
          (fail-open). UI: "Lifecycle hooks" tab in
          frontend/src/components/AdminView.tsx.

8. Plan mode (separate plan-then-approve step)
   [YES] New PlanService (backend/app/services/plan_service.py) drafts
          a structured plan (title/summary/steps) via the
          complex_reasoning model with strict-JSON prompt + heuristic
          fallback; plans persist in backend/app/domain/plan/ and are
          approved/rejected via /api/v1/plans. Execution after approval
          re-runs the agent stream with the approved plan embedded as a
          planPreamble system-prompt prefix (conversations.py +
          agents/orchestrator/nodes.py). UI: "Plan" toggle in
          ChatInput.tsx + PlanReviewCard (Approve & Execute / Reject /
          Dismiss) in ChatArea.tsx.

 MEMORY / CONTEXT / SESSION
=====================================================================
21. Long-term memory (user + project memories)
     [YES] mem0-backed backend memory service; CRUD at
           /api/v1/settings/memories; UI in SettingsView.

22. DYNAMIC CONTEXT GROWTH / CHAT-SIZE INCREASE  <-- your question
     [YES] BOTH sides:
     a) Frontend input box auto-grows as you type and caps, then
        scrolls  -> ChatInput.tsx adjustTextareaHeight
        (Math.min(scrollHeight, ~180px); max-h classes).
     b) Backend conversation grows safely: CONTEXT COMPILER
        backend/app/services/context_compiler.py
        - per-model context limits (llama-3.3-70b / llama-3.1-8b /
          deepseek: 128k tokens; default 32768)
        - token budget = 75% of window, reserving 4096 completion tokens
        - when history exceeds budget, OLD messages are LLM-summarized
          into an episodic summary node while RECENT turns stay intact
        -> wired into BOTH chat endpoints (messages.py, compile_context
          at non-streaming AND streaming paths) + orchestrator history
          compaction in agents/orchestrator/nodes.py.
     => "More context" is handled instead of being truncated blindly.

23. Context-window fallbacks (model routing on overflow)
     [YES] litellm_client.py configures context_window_fallbacks.
